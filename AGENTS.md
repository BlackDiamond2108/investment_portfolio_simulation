# Правила работы над проектом

## Контекст

Проект разрабатывают два человека. Это локальный учебный симулятор
инвестиционного фонда на C++17 и Qt 6 Widgets. Приложение уже реализовано.
Перед изменениями прочитать README.md, docs/project-plan.md и docs/simulation-rules.md.

## Архитектура

- Одно окно MainWindow, общие GameTypes, Portfolio для операций с активами,
  Simulation для игры, GameStorage для JSON.
- Portfolio и Simulation не зависят от Qt. Не переносить расчёты в окно.
- Не добавлять контроллеры, абстрактные хранилища и отдельные сервисы без
  конкретной необходимости. Небольшую задачу решать в существующих файлах.
- Новые файлы допустимы, когда фактическая сложность это оправдывает;
  обновлять карту проекта при изменении структуры.

## Работа вдвоём

Первый участник отвечает за расчётную основу Portfolio/Simulation;
второй — за MainWindow, GameStorage и интеграцию. Роли можно менять по договорённости.

GameTypes.h, CMakeLists.txt и SimulationTests.cpp — общие файлы: перед
параллельной работой договориться, кто редактирует их в конкретной задаче.
При изменении общего интерфейса обновлять вызовы, тесты и описание контракта вместе.
Не перезаписывать чужие изменения и не проводить попутное массовое переименование.
Если изменения пересекаются, описать конкретное пересечение.
Эта инструкция не разрешает запускать дополнительных ИИ-агентов.

## Расчёты и сохранения

- Следовать docs/simulation-rules.md; различать требования и учебные допущения.
- Деньги — int64 в копейках/центах, паи — 1e-6, металл — 0.001 грамма.
  Произведения считать через проверенные операции с широким промежуточным типом.
- Поступления и возврат паёв не являются инвестиционной прибылью.
- Ставка открытого вклада фиксирована; команды проверяют фазу и остатки.
- Ошибка команды или загрузки не должна частично менять игру или RNG.
- Досрочное завершение тоже фиксирует отчёт месяца. Обязательства не исчезают.
- Изменяя GameState, обновлять список полей в GameStorage.cpp и тест сохранения.
  Не менять смысл существующей схемы JSON без изменения schemaVersion.
- Состояние генератора, промежуточная фаза и автопредложение обязательны в сохранении.

## Проверки и документация

Сборка: `cmake -S . -B build`, затем `cmake --build build --parallel 2`.
Проверки: `ctest --test-dir build --output-on-failure`.
После изменения расчётов проверять конкретные суммы и ошибки;
после изменения UI — сценарий windowGame. Для границ чисел использовать санитайзеры.
Не утверждать, что проверка прошла, если она не запускалась или была пропущена.

Интерфейс и пояснения — на русском, идентификаторы C++ — на английском.
Документация Markdown должна отображаться обычным текстом, не HTML-комментарием.
В README.md не добавлять инструкции или разделы про Git и публикацию репозитория.
В отчёте указывать изменения, выполненные проверки и реальные ограничения.
